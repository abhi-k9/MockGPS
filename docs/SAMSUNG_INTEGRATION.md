# Samsung Modes and Routines feasibility

Status,2026-10-24: **Unavailable in this build; no verified supported secure integration contract for One UI9/Android17.** The separate settings switch is off, disabled and explicitly labelled unavailable. It has no stored enable flag, credential or exported control component. Tasker's existing opt-in/revoke path remains independent and functional. This is a blocked integration requirement, not a completed Samsung implementation.

Samsung's [official Bixby support entry](https://www.samsung.com/us/support/answer/ANS00083201/) was reachable and lists “Use Modes and Routines on your Galaxy phone or tablet” (ANS10002538). This consumer support index establishes that native routines exist; it does **not** specify third-party app discovery, action registration, authenticated callbacks or redistribution/signing requirements. The linked article was not retrievable in this environment. No current primary-source SDK contract/licence establishing an ordinary app's supported secure callback was verified. Model/firmware/region differences, Routines+ distribution and One UI9 compatibility therefore remain unverified.

Public third-party examples expose names such as `com.samsung.android.sdk.routines.v3` metadata/providers. Their own reports include reverse-engineered contracts, failed discovery and unverified device behavior. These are research leads, not official support evidence or permission to redistribute Samsung SDK binaries. No decompiled implementation or undocumented provider/permission workaround is included in MockGPS. A shortcut, implicit intent, UI macro or caller-supplied package string does not authenticate Samsung. SmartThings/cloud bridges and built-in Bluetooth monitoring would add a third pathway and are outside this two-integration scope.

To unblock native support, obtain Samsung's current officially supported app-action documentation and SDK/distribution terms for the target device/region; verify discovery and action execution on an actual One UI9 phone. Establish caller authentication (documented signature-protected permission with verified signer/UID, or a separate revocable capability), immutable typed inputs and process/reboot ordering. Never reuse the Tasker capability for Samsung. Then add independently persisted opt-in/revocation, migration and instrumentation/phone tests before enabling the switch.

Current arbitration is deliberately simple: **Tasker is the only enabled-capable vehicle source**, authenticated by capability possession, not proven package identity. No state from Samsung is accepted. Higher counters cannot turn older DISCONNECTED observations into a resume request; the timestamp watermark never regresses, safety wins ties, and FORCE_REAL persists. Disabling Tasker stops/cancels, revokes its token and requires fresh reconciliation; enabling Samsung is impossible. There is no dual-enabled runtime to claim tested.

Before adding a real second provider, require fresh DISCONNECTED consensus from **both** enabled sources, with independent source epochs and replay/freshness state; any CONNECTED/UNKNOWN, source change, revocation, recovery or missing reconciliation invalidates pending starts. Both observations must postdate the last safety watermark. One shared reducer/provider controller must remain authoritative. This is the required future policy, not a claim that a nonexistent Samsung endpoint was implemented/tested.

Owner phone check: keep Samsung off; use the verified manual Tasker path if desired. Record One UI/Modes and Routines/Routines+ versions, region and whether Samsung offers an officially documented third-party app-action mechanism. Do not configure an unauthenticated broadcast or macro as a substitute. There is no Samsung action to install or roll back in this candidate. Tasker setup/rollback is in [the import guide](../tasker/README.md); all complete physical safety cases remain [NOT RUN](SAMSUNG_VALIDATION.md).
